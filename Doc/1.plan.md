# 1. পরিকল্পনা (Plan)

শেষ হালনাগাদ: 2026-10-29

## লক্ষ্য
এক বিক্রেতার (single vendor) বাংলাদেশি অনলাইন দোকান "মেলা"। শুরুতে ক্যাশ অন ডেলিভারি (COD), পরে অনলাইন পেমেন্ট। ছোট, নিরাপদ আর কম খরচের সমাধান।

## ঠিক হয়ে যাওয়া সিদ্ধান্ত
| বিষয় | সিদ্ধান্ত |
|---|---|
| দোকানের ধরন | Single vendor (একটাই দোকান, marketplace নয়) |
| ভাষা ও মুদ্রা | বাংলা UI, টাকা (৳) |
| পেমেন্ট (এখন) | ক্যাশ অন ডেলিভারি |
| Frontend | Static HTML/CSS/JS, কোনো build step নেই |
| Backend ও database | Supabase (Postgres + Row Level Security + database functions) |
| ক্রেতার লগইন | ইমেইল + পাসওয়ার্ড; লগইন ছাড়াও অর্ডার চলবে; ইমেইল যাচাই এখন বন্ধ, launch-এর আগে চালু ([9.auth.md](9.auth.md)) |
| stock শেষ হলে | অর্ডার বন্ধ, বাতিল হলে stock ফেরত ([11.orders-safety.md](11.orders-safety.md)) |
| spam সীমা | একই ফোন নম্বরে ঘণ্টায় সর্বোচ্চ 3টি অর্ডার |
| ডেলিভারি ফি | ৳60, তবে পণ্যের দাম ৳2000 বা তার বেশি হলে ফ্রি |
| উপহার প্যাক | প্রতি পণ্যে +৳60 |

খোলা সিদ্ধান্তগুলো আছে [3.business-rules.md](3.business-rules.md)-এ।

## এখনকার অবস্থা (2026-10-29)
| কাজ | অবস্থা |
|---|---|
| দোকানের পেজ: home, shop, product, wishlist, cart, order-placed, account | কোড `main`-এ আছে। মালিক নিজে ব্রাউজারে চালিয়েছেন: শোরুম, অর্ডার দেওয়া, নাম escape (X10) পাস। বাকি পেজগুলোর সব কাজ পুরো তালিকা ধরে পরীক্ষা হয়নি। |
| Supabase schema, সুচক, অর্ডারের অবস্থার নিয়ম (trigger), audit লগ, stock, ডুপ্লিকেট ও spam সীমা | প্রয়োগ হয়েছে (চারটি migration সফল)। `place_order`, অবস্থার নিয়ম ও stock/spam SQL দিয়ে যাচাই হয়েছে ([10.admin.md](10.admin.md), [11.orders-safety.md](11.orders-safety.md))। |
| পণ্য ও ক্যাটাগরি Supabase থেকে লোড, অর্ডার সেভ | বাস্তবে কাজ করছে: মালিকের দুটি অর্ডার (M000001, M000002) তৈরি হয়েছে। |
| ক্রেতার লগইন, পাসওয়ার্ড রিসেট, অর্ডার ইতিহাস (ধাপ C) | কোড আছে। লগইন করা অর্ডারের ইতিহাস কাজ করেছে (M000002)। পাসওয়ার্ড রিসেট ও বাকি পরীক্ষা [9.auth.md](9.auth.md)-এ দেখুন। |
| Admin panel (ধাপ D) | মালিক ব্রাউজারে চালিয়েছেন: 10টি পাস, X7 এর সমস্যা (guest অর্ডারের অবস্থা ক্রেতা পান না), X12 বাকি ([10.admin.md](10.admin.md))। |
| পেমেন্ট, নোটিফিকেশন | বাকি |

## কাজের ধাপ
অগ্রাধিকার: **P0** = নিরাপদ launch-এর জন্য জরুরি, **P1** = production-এর জন্য দরকার, **P2** = বাড়ার পর।

| ধাপ | কাজ | অগ্রাধিকার | অবস্থা |
|---|---|---|---|
| A | দোকানের frontend | P0 | কোড হয়েছে, আংশিক পরীক্ষা |
| B | Database ও অর্ডার সেভ | P0 | কাজ করছে (বাস্তব অর্ডার দিয়ে দেখা) |
| C | ক্রেতার লগইন (ইমেইল) ও অর্ডার ইতিহাস | P0 | কোড হয়েছে, আংশিক পরীক্ষা |
| D | Admin panel: পণ্য যোগ-বদল, অর্ডার দেখা ও status বদলানো | P0 | কোড হয়েছে, মালিক পরীক্ষা করেছেন (X7, X12 বাকি) |
| E | Stock যাচাই ও কমানো, ডুপ্লিকেট অর্ডার ঠেকানো, spam সীমা | P0 | কোড ও DB হয়েছে, DB যাচাই হয়েছে, ব্রাউজার পরীক্ষা বাকি |
| E2 | backup যাচাই (আপনার Supabase প্ল্যানে) | P0 | বাকি |
| F | অনলাইন পেমেন্ট (sandbox আগে), SMS/ইমেইল নোটিফিকেশন, ডেলিভারি ট্র্যাকিং, রিটার্ন/রিফান্ড | P1 | বাকি |
| G | Performance, staging পরিবেশ, CI, SEO-র মূল কাজ | P1 | বাকি |
| H | রিভিউ, analytics, abandoned-cart, কুপন | P2 | দরকার হলে |

নিরাপত্তা আর data সঠিক থাকার কাজ শেষের ধাপে ফেলে রাখা হবে না, প্রতিটি ধাপেই করা হবে ([6.security.md](6.security.md))।

## এখন দরকার নেই (skip)
| বাদ দেওয়া বিষয় | কেন | কখন আবার ভাবব |
|---|---|---|
| Multi-vendor, seller onboarding | Single vendor | দোকান marketplace হলে |
| Microservices, queue, distributed cache | Modular monolith-ই যথেষ্ট | মাপা bottleneck দেখা দিলে |
| Multi-currency, multi-language | শুধু বাংলাদেশ, বাংলা, টাকা | অন্য দেশে বিক্রি শুরু হলে |
| Enterprise disaster recovery (RTO/RPO মহড়া), failure-boundary test | এই আকারে অতিরিক্ত | ব্যবসা বড় হলে। সাধারণ backup আর restore পরীক্ষা তবু দরকার। |
| Marketing automation, A/B test, advanced fraud monitoring | এখন ট্রাফিক নেই | বিক্রি বাড়লে |
| CDN আলাদা করে সাজানো | শুরুতে ছবি কম, পণ্য emoji দিয়ে দেখানো | আসল ছবি ব্যবহার শুরু হলে |
| ফোন নম্বর + OTP লগইন | SMS খরচ ও আলাদা provider লাগে | ইমেইল লগইন থেকে ক্রেতারা সরে গেলে |
| CAPTCHA | আপনি ফোন-সীমা বেছেছেন | বড় আকারের spam আক্রমণ হলে |

## কাজের নিয়ম (সংক্ষেপে)
- ছোট ছোট ধাপে কাজ, প্রতিটি যাচাই করে।
- আগে থেকে থাকা কাজ ভাঙব না, বড় rewrite করব না।
- ক্রেতার ব্রাউজার থেকে আসা দাম, stock, role বা payment status বিশ্বাস করা হবে না।
- পাসওয়ার্ড, secret key (`service_role` সহ) চ্যাটে বা repo-তে রাখা হবে না।
- যা পরীক্ষা হয়নি সেটা "কাজ করছে" বলে লেখা হবে না।
- আপনার সিদ্ধান্ত দরকার হলে প্রশ্ন-উত্তরের popup-এ জিজ্ঞেস করা হবে, সুপারিশ চিহ্নিত করে।
