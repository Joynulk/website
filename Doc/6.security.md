# 6. Security

চিহ্ন: ✅ আছে (কোডে বা database-এ), ⚠️ আংশিক বা পরীক্ষা বাকি, ❌ নেই।

"আছে" মানে কোডে বা schema-তে বসানো হয়েছে। যেগুলো Supabase-এ SQL চালিয়ে যাচাই হয়েছে সেগুলোতে "যাচাই" লেখা আছে। ব্রাউজারে মালিক যা চালিয়েছেন তা [10.admin.md](10.admin.md)-এর টেবিলে আছে; বাকি পরীক্ষা [7.testing.md](7.testing.md), [9.auth.md](9.auth.md), [11.orders-safety.md](11.orders-safety.md)-এ।

## অ্যাক্সেস ও অনুমতি
| বিষয় | অবস্থা | মন্তব্য |
|---|---|---|
| সব টেবিলে Row Level Security | ✅ | Supabase advisor-এ RLS-এর অভাবের কোনো সতর্কতা আসেনি (2026-10-29 আবার দেখা) |
| Admin ও ক্রেতা আলাদা | ⚠️ | `admins` টেবিল + `is_admin()` + RLS আছে। মালিকের পরীক্ষায় admin ঢোকা/না ঢোকা পাস (X1-X3); সাধারণ ক্রেতার token দিয়ে সরাসরি লেখার চেষ্টা (X12) বাকি |
| ক্রেতা শুধু নিজের অর্ডার দেখে | ⚠️ | নিয়ম আছে, লগইন করা অর্ডার নিজের সারিতে এসেছে (M000002 বাতিল অবস্থাসহ দেখা গেছে); অন্য ক্রেতার অর্ডার দেখার চেষ্টার পরীক্ষা (A11) বাকি |
| Client থেকে আসা দাম/role অবিশ্বাস | ✅ | `place_order` নিজে দাম হিসাব করে (SQL-এ যাচাই: মোট 5040 ঠিক এসেছে; মালিকের অর্ডারগুলোতেও ঠিক দাম) |
| অর্ডারের তথ্য পরে বদলানো | ✅ | trigger শুধু `status` বদলাতে দেয়, admin-ও নাম/ঠিকানা/দাম বদলাতে পারে না (SQL-এ যাচাই) |
| অবস্থা বদলের বৈধ পথ | ✅ | pending -> shipped -> delivered, অথবা cancelled; শেষ অবস্থা আর বদলায় না (SQL-এ যাচাই, মালিকের ব্রাউজার পরীক্ষায়ও X5, X6 পাস) |
| ক্রেতার লগইন ও session | ⚠️ | Supabase Auth ব্যবহার করা হয়েছে, নিজে পাসওয়ার্ড রাখি না। লগইন ও অর্ডার মালিকের হাতে চলেছে; নিয়মিত পরীক্ষার তালিকা ([9.auth.md](9.auth.md)) বাকি |
| Token সংরক্ষণ | ⚠️ | localStorage-এ। XSS হলে ঝুঁকি। [Boundary.md](Boundary.md) দেখুন |
| ইমেইল যাচাই | ❌ | আপনার সিদ্ধান্তে এখন বন্ধ, launch-এর আগে চালু করতে হবে |

## অর্ডার ও stock
| বিষয় | অবস্থা | মন্তব্য |
|---|---|---|
| Input যাচাই (সার্ভারে) | ✅ | ফোন, নাম, ঠিকানা, সংখ্যা |
| Overselling ঠেকানো | ✅ | `place_order` stock এক ধাপে যাচাই ও কমায় (SQL-এ যাচাই)। ব্রাউজার পরীক্ষা বাকি (S1-S5) |
| ডুপ্লিকেট অর্ডার ঠেকানো | ✅ | অনন্য `p_key` + unique index (SQL-এ যাচাই)। ব্রাউজার পরীক্ষা বাকি (S6) |
| Spam/অপব্যবহার সীমা | ⚠️ | এক ফোনে ঘণ্টায় সর্বোচ্চ 3টি (SQL-এ যাচাই)। সীমা শুধু ফোন নম্বরের, অন্য নম্বর বাবহার করে এইটা এড়ানো যায়; CAPTCHA বা IP সীমা নেই ([11.orders-safety.md](11.orders-safety.md))। ব্রাউজার পরীক্ষা বাকি (S7) |
| Audit trail (কে কখন status বদলাল) | ✅ | `order_events` লগ আছে, মালিকের অর্ডারগুলোতে লগ জমেছে (M000001: 2টি, M000002: 1টি)। admin panel-এ দেখানো হয় নি |

## Frontend
| বিষয় | অবস্থা | মন্তব্য |
|---|---|---|
| XSS (পণ্যের নাম, বিবরণ, ক্যাটাগরি, সার্চ শব্দ) | ✅ | সব জায়গায় `esc()` বা `textContent` ব্যবহার হয়। রঙের মান `#rrggbb` ছাড়া গ্রহণ হয় না। মালিকের ব্রাউজার পরীক্ষায় `<b>টেস্ট</b>` হুবহু লেখা দেখায় (X10 পাস) |

| HTTPS | ⚠️ | Supabase ও GitHub Pages দুটোই HTTPS দেয়। নিজের domain হলে চালু আছে কি না দেখে নিন |

## Supabase security advisor (2026-10-29, ধাপ D-র পর আবার চালানো)
3টি সতর্কতা, সবই "SECURITY DEFINER function সবাই ডাকতে পারে"। ধাপ E-র পর আবার চালানো হয়নি (`place_order` কে সমান নামে নতুন স্বাক্ষরে বানানো হয়েছে, তাই আবার চালানো দরকার):
- `place_order`: ইচ্ছাকৃত, কারণ ক্রেতা লগইন ছাড়াই অর্ডার করে।
- `is_admin`: দরকারি, কারণ RLS নিয়ম ও admin panel এটা ডাকে। শুধু true/false দেয়।
- `rls_auto_enable`: আমাদের বানানো নয়, Supabase-এর। কী করে জানা ও দরকার না হলে বন্ধ করার কথা ভাবা বাকি।

## পেমেন্ট যোগ করার সময় অবশ্যই (ধাপ F)
- কার্ডের তথ্য নিজেদের সিস্টেমে বা লগে রাখা যাবে না। Gateway-র hosted পেজ ব্যবহার।
- ব্রাউজারে "সফল" পেজ দেখে অর্ডার নিশ্চিত করা যাবে না। Gateway-র সার্ভার থেকে আসা যাচাই করা বার্তাই (webhook বা verify API) সত্য।
- Webhook-এর signature যাচাই, ডুপ্লিকেট event ঠেকানো, বিলম্বে বা উল্টো ক্রমে আসা event সামলানো।
- Payment আর order status-এর বদল স্পষ্ট ও লগ করা।
- আগে sandbox, তারপর আসল।
