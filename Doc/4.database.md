# 4. Database

Project: Supabase `gjawsgadcwqlohvfakzp` (Postgres 17, region ap-southeast-2)। শুরুর schema: `supabase/schema.sql` (প্রয়োগ হয়েছে `mela_phase2_schema` নামে)। পরের পরিবর্তন: `supabase/migrations/` (`002_order_indexes.sql`, `003_order_guard_and_audit.sql`, দুটোই প্রয়োগ হয়েছে)।

## টেবিল
| টেবিল | মূল কলাম | মন্তব্য |
|---|---|---|
| `categories` | id (text), name, emoji, color, sort | "সব দোকান" এখানে নেই, সেটা frontend-এ |
| `products` | id, name, category_id, price (>=0), emoji, description, stock, active, created_at | `active=false` হলে ক্রেতা দেখে না |
| `orders` | id (text), user_id, name, phone, address, subtotal, shipping, total, status, created_at | status শুধু 4টি মান। লগইন থাকলে `user_id` বসে, না হলে খালি। তৈরির পর শুধু `status` বদলাতে পারে (trigger) |
| `order_items` | id, order_id, product_id, name, emoji, unit_price, qty (>0) | অর্ডারের সময়ের নাম ও দাম এখানে কপি থাকে |
| `order_events` | id, order_id, from_status, to_status, changed_by, created_at | প্রতিটি status বদলের লগ (audit)। শুধু admin পড়তে পারে |
| `admins` | user_id | এখানে থাকলেই admin |
| `order_seq` | sequence | অর্ডার নম্বরের জন্য |

ক্রেতার অ্যাকাউন্ট Supabase Auth-এর (`auth.users`) ভেতরে। ডেলিভারির সংরক্ষিত তথ্য ওই user-এর `user_metadata`-তে। আলাদা টেবিল নেই ([9.auth.md](9.auth.md))।

## সুচক (index)
`orders(user_id)`, `orders(created_at desc)`, `order_items(order_id)`, `products(category_id)`, `order_events(order_id)`। সব টেবিলে primary key-এর index আগে থেকেই আছে।

## নিরাপত্তার নিয়ম (Row Level Security)
সব টেবিলে চালু।

| টেবিল | কে পড়তে পারে | কে লিখতে পারে |
|---|---|---|
| categories | সবাই | শুধু admin |
| products | সবাই (active পণ্য), admin সব | শুধু admin |
| orders | নিজের অর্ডার (user_id মিললে), admin সব | সরাসরি insert নয়। শুধু admin update পারে (ও শুধু status, নিয়মের ভেতরে) |
| order_items | নিজের অর্ডারের আইটেম, admin সব | সরাসরি লেখা যায় না |
| order_events | শুধু admin | শুধু trigger (বাইরে থেকে নয়) |
| admins | নিজের সারি | কেউ নয় (dashboard বা SQL থেকে বসাতে হয়) |

## Function
| নাম | কাজ |
|---|---|
| `place_order(p_name, p_phone, p_address, p_items)` | তথ্য যাচাই, দাম ও মোট হিসাব, অর্ডার ও আইটেম তৈরি, `{id, total}` ফেরত। `security definer`, anon ও logged-in ব্যবহার করতে পারে। |
| `is_admin()` | বর্তমান ব্যবহারকারী admin কি না। RLS নিয়মগুলো এটা ব্যবহার করে, admin panelও এটা ডাকে। |
| `guard_order_update()` (trigger `orders_guard`) | অর্ডার update-এ শুধু `status` বদলানোর অনুমতি, বৈধ পথ যাচাই, `order_events`-এ লগ। বাইরে থেকে ডাকা যায় না। নিয়ম: [10.admin.md](10.admin.md) |

## প্রথম admin বানানো
[10.admin.md](10.admin.md)-এ ধাপগুলো আছে। সংক্ষেপে: আগে ইমেইল দিয়ে সাইন আপ করুন, তারপর Supabase SQL Editor-এ:
```sql
insert into admins(user_id) select id from auth.users where email = 'আপনার-ইমেইল';
```

## পরিবর্তনের নিয়ম
- Schema বদলাতে নতুন ফাইল: `supabase/migrations/NNN_নাম.sql` (পুরনো ফাইল সম্পাদনা নয়)।
- প্রতিটি ফাইলের সাথে উল্টানোর (rollback) SQL একই ফাইলের নিচে মন্তব্য হিসেবে লিখে রাখা।
- Migration চালানোর পর Supabase security advisor ও `place_order` একবার চালিয়ে দেখা (শেষে rollback করা পরীক্ষার নমুনা [7.testing.md](7.testing.md)-এ)।
- কোনো টেবিলে RLS বন্ধ রাখা যাবে না।

## জানা ফাঁক (এখনো করা হয়নি)
| ফাঁক | কেন গুরুত্বপূর্ণ | করণীয় |
|---|---|---|
| `place_order` stock কমায় না, stock যাচাইও করে না | বেশি বিক্রি (overselling) হতে পারে | ধাপ E: একই transaction-এ stock কমানো, না থাকলে ব্যর্থ |
| ডুপ্লিকেট অর্ডার ঠেকানোর key নেই | নেটওয়ার্ক retry বা দুইবার চাপে একই অর্ডার দুইবার হতে পারে | ধাপ E: ক্লায়েন্ট থেকে একটা অনন্য `idempotency_key` নিয়ে `orders`-এ unique করা |
| Payment status কলাম নেই | অনলাইন পেমেন্টে লাগবে | ধাপ F-এ `payment_status`, `payment_ref` যোগ |
| Guest অর্ডার পরে দেখা যায় না, অ্যাকাউন্টেও যুক্ত হয় না | `user_id` খালি | ফোন + অর্ডার নম্বর দিয়ে খোঁজার ব্যবস্থা বা বাস্তবে পরে যুক্ত করার ব্যবস্থা ভাবা |
| Admin panel-এ audit লগ দেখানো হয় না | লগ আছে, UI নেই | Table Editor-এ দেখা যায়; পরে পেজে যোগ |
